# opensource-repo-analytics

GitHub repo analytics pipeline (Bronze/Silver/Gold) for open-source project health metrics.



\## Sample data

\- `raw/full/2026-08-15/full\_load\_sample.json`: snapshot of commits, issues and PRs for all 4 repos up to the cutoff 2026-08-15.

\- `raw/incremental/2026-09-30/incremental\_load\_sample.json`: new and updated records after the cutoff, downloaded on 2026-09-30 using the `since` parameter.

\- Generated by `extract\_samples.py` using the GitHub REST API.


## Pipeline overview (Phase 2)

Raw JSON Lines (GitHub API) -> **Staging** (explicit schema, bad rows flagged) -> **Bronze** (MERGE) -> **Silver** (flatten, cast, hash PII, MERGE).
Platform: Databricks Free Edition (serverless), catalog `workspace`. Every table has `load_timestamp`.

| Notebook | Purpose |
|---|---|
| `00_setup` | Creates schemas `landing`, `bronze`, `silver`, `ops` and volume `landing.raw` |
| `00_logging` | Creates `ops.pipeline_execution_logs` and the `write_log()` helper |
| `00_extract` | Runs `extract_raw.py` (full / incremental extraction into the volume) |
| `01_config_schemas` | Explicit `StructType` schemas and primary keys (`SCHEMAS`, `KEYS`) |
| `02_raw_to_bronze` | Raw -> staging -> quarantine / Bronze `MERGE` |
| `03_bronze_to_silver` | Bronze -> Silver transform, data-quality quarantine, `MERGE` |

Raw layout: `/Volumes/workspace/landing/raw/<full|incremental>/<batch_date>/<owner__repo>/<commits|issues|pulls>/page_NNNN.jsonl`

## Bronze data model (schema-on-read, no inferSchema)

Common metadata columns on every Bronze table: `source_file` STRING, `batch_date` STRING, `load_type` STRING, `load_timestamp` TIMESTAMP.

**`bronze.commits`** - PK: `repo_name`, `sha`
| Column | Type |
|---|---|
| repo_name, entity_type, sha | STRING |
| commit | STRUCT(author, committer: STRUCT(name, email, date STRING); message STRING; comment_count LONG) |
| author, committer | STRUCT(login STRING, id LONG, type STRING) |

**`bronze.issues`** (issues and PR stubs as returned by `/issues`) - PK: `repo_name`, `id`
| Column | Type |
|---|---|
| repo_name, entity_type, title, state | STRING |
| id, number, comments | LONG |
| user | STRUCT(login, type STRING; id LONG) |
| labels | ARRAY<STRUCT(id LONG, name STRING)> |
| created_at, updated_at, closed_at | STRING (cast in Silver) |
| pull_request | STRUCT(url STRING), non-null when the item is a PR |

**`bronze.pulls`** (details from `/pulls/{number}`) - PK: `repo_name`, `id`
| Column | Type |
|---|---|
| repo_name, entity_type, title, state | STRING |
| id, number, comments, review_comments, commits, additions, deletions, changed_files | LONG |
| user | STRUCT(login, type STRING; id LONG) |
| created_at, updated_at, closed_at, merged_at | STRING |
| merged | BOOLEAN |

**`bronze.quarantine`**: `entity`, `batch_date`, `load_type`, `source_file`, `raw_record` (original JSON line), `load_timestamp`.

## Silver data model (typed, flattened, PII handled)

PII handling: email addresses are SHA-256 hashed; author name and avatar/profile URLs are not carried into Silver. GitHub login is kept (public pseudonymous identifier).

**`silver.commits`** - PK: `repo_name`, `sha`
`repo_name` STRING, `sha` STRING, `commit_message` STRING, `author_login` STRING, `committer_login` STRING, `author_email_hash` STRING, `committer_email_hash` STRING, `commit_date` TIMESTAMP, `batch_date` STRING, `load_type` STRING, `load_timestamp` TIMESTAMP

**`silver.issues`** - PK: `repo_name`, `id`
`repo_name` STRING, `id` LONG, `number` LONG, `title` STRING, `state` STRING, `is_pr` BOOLEAN, `user_login` STRING, `label_count` INT, `comments` LONG, `created_at_ts` TIMESTAMP, `closed_at_ts` TIMESTAMP, `updated_at_ts` TIMESTAMP, `time_to_close_hours` DOUBLE, `batch_date` STRING, `load_type` STRING, `load_timestamp` TIMESTAMP

**`silver.pulls`** - PK: `repo_name`, `id`
`repo_name` STRING, `id` LONG, `number` LONG, `title` STRING, `state` STRING, `merged` BOOLEAN, `user_login` STRING, `comments` LONG, `review_comments` LONG, `commits` LONG, `additions` LONG, `deletions` LONG, `changed_files` LONG, `created_at_ts` TIMESTAMP, `closed_at_ts` TIMESTAMP, `merged_at_ts` TIMESTAMP, `updated_at_ts` TIMESTAMP, `time_to_merge_hours` DOUBLE, `batch_date` STRING, `load_type` STRING, `load_timestamp` TIMESTAMP

**`silver.quarantine`**: `entity`, `batch_date`, `load_type`, `reason`, `record` (JSON), `load_timestamp`. Rows with a null key or an unparseable date go here and the batch continues.

## Operational table: `ops.pipeline_execution_logs`

`log_id`, `layer` (`raw_to_bronze` / `bronze_to_silver`), `entity`, `parameter` (`<load_type>/<batch_date>/<entity>`), `load_type`, `start_time`, `end_time`, `status` (SUCCESS / FAILURE), `rows_inserted`, `rows_updated`, `error_message` (failure text or notes such as `quarantined_rows=N`), `load_timestamp`.

## Robustness design

- **Idempotency:** Bronze and Silver load with `MERGE INTO` on the primary keys. Re-running the same batch inserts 0 rows. Issues, PRs and their Silver tables only update when the incoming `updated_at` is not older than the stored one.
- **Schema contract and drift:** schemas are explicit `StructType`s. Records that do not match (for example a type change) are flagged as corrupt and quarantined without stopping the batch. Delta `MERGE WITH SCHEMA EVOLUTION` lets target tables evolve.
- **Serverless note:** caching is unavailable, so each batch is written to a temporary staging table before quality checks.

## Execution guide

All notebooks take parameters through widgets.

| Widget | Meaning |
|---|---|
| `batch_date` | Folder name under the load type, e.g. `2026-10-01` |
| `load_type` | `full` or `incremental` |
| `entity` | `all`, `commits`, `issues` or `pulls` |
| `raw_root` | Raw landing path (Bronze notebook), default `/Volumes/workspace/landing/raw` |

**Standard incremental run (daily)**
1. `00_extract`: `run_extract("--mode", "incremental", "--out", "/Volumes/workspace/landing/raw")` (uses the saved watermark as `since`; creates folder `incremental/<today>`).
2. `02_raw_to_bronze`: `batch_date=<today>`, `load_type=incremental`, `entity=all`.
3. `03_bronze_to_silver`: same parameters.

**Initial full load**
1. `00_extract`: `run_extract("--mode", "full", "--start", "2025-10-01T00:00:00Z", "--until", "2026-10-01T00:00:00Z", "--out", "/Volumes/workspace/landing/raw")`.
2. Bronze then Silver with `batch_date=2026-10-01`, `load_type=full`, `entity=all`.

**Backfill (re-process any historical batch, no re-download)**
Set `batch_date` (and `load_type`) to the historical folder, optionally `entity` to one table, and run `02_raw_to_bronze` then `03_bronze_to_silver`. To read from another location, change `raw_root`. Because loads are `MERGE`s, backfills never create duplicates.

**Check results:** query `ops.pipeline_execution_logs` for status and row counts per run.
